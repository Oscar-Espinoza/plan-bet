## The core rule

Legacy took `pg_advisory_xact_lock(4, user)` and then re-read membership, game availability, price and balance inside the transaction. D1 has no locks, but it serializes writes and runs `db.batch()` as one transaction. So **each check that must hold at write time becomes a SQL predicate inside the write batch**. A read before the batch only picks the error message or pre-validates pure values. It never decides on its own that a write is safe.

## Pieces

1. **`src/lib/server/data/credits.ts`:** port `STARTING_CREDITS`, `SUMMARY_PROJECTION` (SQLite has aggregate `FILTER (WHERE …)`; drop the `::bigint`/`::int` casts, since SQLite integers are 64-bit, but keep `toSafeInteger`), `toSummary`, `getCreditSummary` and `readBalance`. Extend what T07 added; don't duplicate it.
   - `resetBankroll` becomes **one statement**:
     ```
     INSERT INTO credit_entries (id, user_id, kind, amount, reason, created_at)
     SELECT ?, ?, 'reset', max(-2147483647, min(2147483647, 1000 - (SELECT coalesce(sum(amount),0) FROM credit_entries WHERE user_id = ?))), 'manual_reset', ?
     WHERE (SELECT count(*) FROM credit_entries WHERE user_id = ? AND kind = 'reset' AND created_at >= ?) < 5
     ```
     Use the legacy constants rather than literals. `meta.changes === 0` means `rate_limited`. Run the summary read in the same `db.batch()`. A reset inserts a row even at delta 0.
2. **`src/lib/server/data/wagers.ts`:** port `evaluateWagerAvailability` verbatim, plus `placeWager` with the same signature and the same `PlaceWagerResult` reasons and **precedence**:
   1. **Pre-reads, outside the batch, in legacy order:**
      - An idempotency key that already has a wager is a replay: return it with `replayed: true` and the summary.
      - Group membership: a non-member gets `not_a_group_member`.
      - Game by route id: a missing game is `unavailable`.
      - `resolveSelection`: no match is `invalid_selection`.
      - `evaluateWagerAvailability`: not open is `closed` with its status.
      - Client price ≠ house price: `price_moved` with the house price.
   2. **One write batch:**
      - (a) `INSERT INTO wagers … SELECT … WHERE` *balance ≥ stake* AND *the game row is still open* AND *membership still holds* (when `groupId` is set) `ON CONFLICT (user_id, idempotency_key) DO NOTHING`. "Still open" is the SQL form of `evaluateWagerAvailability`: `games.status = 'scheduled'`, `games.scheduled_at > now`, and `json_extract(games.summary, '$.result') IS NULL`, matched by the canonical id the pre-read found.
      - (b) `INSERT INTO credit_entries (… kind 'stake', amount -stake, reason 'wager placed', wager_id) SELECT … WHERE EXISTS (SELECT 1 FROM wagers WHERE id = ?newId)`.
      - (c) Read back the wager by `id = ?newId`, or by `(user_id, idempotency_key)` when a key was sent.
      - (d) The summary.
   3. **After the batch:**
      - If (c) returned the new id, it's a success with `replayed: false`.
      - If it returned a different id (a concurrent same-key placement won), it's `replayed: true`.
      - If nothing was inserted, re-run the legacy checks as reads to choose the reason: membership, then availability (`closed`), else `insufficient_balance`.
   4. Group activity email: after a fresh success with a `groupId`, call the ported `notifyGroupWagerPlaced` through `waitUntil` from `cloudflare:workers`. Never on a replay. If `group-notifications.ts` isn't ported yet, port only what this call needs (Resend over fetch, opt-out respected) and say so in the log.
   5. `potentialReturn = Math.round(stake * selection.price)`; the price is frozen through the `price_hundredths` custom type. Labels, matchup, competition, versions and `scheduledAt` are the same as legacy.
3. **`src/lib/server/data/wagers-repository.ts`:** port every export of the legacy file to D1 (`readGameForWager`, `rowToWager`, `listWagersForGame`, `listWagersForGroup`, `listGroupMatchActivity`, `listGroupWagersForGame`, `listWagers`, `listWagerHistory`, plus whatever T07 added). Keep pagination semantics, ordering `(created_at DESC, id DESC)` as the tiebreak, and the joins that bring settlement and final score into history in one query.
4. **Routes**, `src/routes/api/bets/+server.ts` (GET, POST) and `src/routes/api/bets/reset/+server.ts` (POST): port the legacy handlers, with the same status codes, error codes and envelopes. Keep the guard order `isSameOrigin` → `requireAccount` → `readJsonBody` and the same Zod request contracts. The maintenance switch from T07 already covers these.
5. **Verification scripts** (migration tooling, not a test suite; no test framework):
   - `scripts/verify/money-scenario.ts`, run with `node --experimental-strip-types` or `tsx`, against a base URL (`--base http://localhost:8787`) with a session cookie. It creates its own user and session in the local D1, using `wrangler d1 execute --local` and T07's cookie format, then runs these over HTTP:
     - (1) a place succeeds;
     - (2) the same idempotency key again gives one wager, one debit, `replayed: true`;
     - (3) the same intent with a new key makes a second wager;
     - (4) an overdraw (stake > balance) is `insufficient_balance`, with no rows written (compare counts before and after);
     - (5) a closed game is `closed` (use a game whose stored status isn't `scheduled`, or seed one);
     - (6) a group the user isn't in is `not_a_group_member`;
     - (7) a wrong price is `price_moved`;
     - (8) **20 concurrent placements** whose stakes together exceed the balance: the final balance is ≥ 0, every success has exactly one `stake` row, and the count of successes × stake ≤ the starting balance;
     - (9) six resets inside an hour: the sixth returns the rate-limited error;
     - (10) a reset at delta 0 still inserts a row.
     It prints `MONEY SCENARIO OK` only if every step passed, and otherwise prints each failure and exits 1.
   - `scripts/verify/ledger-invariants.sql` returns one row per violation, and zero rows means clean:
     - a wager with no `stake` entry, or more than one;
     - a `stake` entry whose amount ≠ -wager.stake;
     - more than one `return` per wager;
     - more than one `grant` per user;
     - a user whose balance is below 0;
     - a `return` entry without an outcome, or an outcome on a non-return.
     Add `pnpm verify:money` to run both against local and print `LEDGER INVARIANTS OK` when the SQL returns 0 rows.
