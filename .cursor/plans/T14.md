## What you build

Three scripts under `scripts/migrate/`, run with `pnpm dlx tsx` or `node --experimental-strip-types` (whichever works for the TypeScript you write; check it runs). Output goes to `migration-out/` (gitignored).

1. **`export-neon.ts --url-env <VAR> --env-file <path>`:** connects with the `postgres` npm package (add it as a dev dependency) using the connection string in env var `<VAR>` loaded from `<path>`. It runs **read-only** `SELECT *` per table, ordered by primary key, inside one `REPEATABLE READ READ ONLY` transaction so the snapshot is consistent. It writes one NDJSON file per table plus `manifest.json` with row counts and the export timestamp. It never writes to the source.
2. **`transform.ts`:** reads the NDJSON and writes `migration-out/import.sql` for D1.
   - Type rules from spec §3.6: uuid → text; timestamptz → integer ms; jsonb → JSON text; `text[]` → JSON text; enums as is; price → `price_hundredths = round(price*100)`; line → `line_tenths = round(line*10)`.
   - **Auth.js → Better Auth:**
     - `users` → `user`. Ids are preserved. `name` = legacy name, else the email local part, else `"User"`. `email` is required: a legacy user with no email is skipped and listed in `manifest-transform.json` with the reason, and the transform fails if such a user owns wagers or ledger rows. `emailVerified` = legacy `email_verified IS NOT NULL`. `created_at`/`updated_at` come from the legacy timestamps, else the export time.
     - `accounts` → `account`: id = a new uuid, `accountId` = `providerAccountId`, `providerId` = `provider`, and the tokens and expiry are mapped.
     - `sessions` and `verification_tokens` are **not** migrated.
   - Table order respects foreign keys. Start with `PRAGMA defer_foreign_keys = true;`.
   - **`DROP TRIGGER IF EXISTS user_starting_grant;` before the user inserts, and recreate it at the end with SQL byte-identical to the migration.** Otherwise every imported user gets a second grant and the import fails on `credit_entries_user_grant_uidx`.
   - Every statement stays under 100 KB. Multi-row inserts are fine. Values are SQL literals, escaped correctly; test with quotes, newlines, unicode and emoji in names and comments.
   - Tables not migrated (`sessions`, `verification_tokens`) are listed in the manifest.
3. **`reconcile.ts --source <ndjson dir> --d1 <local|preview|prod>`:**
   - It reads D1 via `wrangler d1 execute ... --json`, with `--local` for local; preview uses `--remote --env preview`; **prod is refused by the script unless the env var `MP_RECONCILE_PROD=1` is set**.
   - Per user, it compares against the source: balance, wager count, open wagers (no return), sum of stakes and sum of returns.
   - Per table, it compares row counts with the source, minus the documented skips.
   - It prints `RECONCILE OK users=<n> tables=<n>` only on an exact match; otherwise it prints each mismatch and exits 1.
   - It also runs `scripts/verify/ledger-invariants.sql` and requires zero rows.

## Local rehearsal (no production access in this ticket)

- Start a throwaway Postgres in Docker. Use a container named `t14-pg`, port 55432, with `docker run --rm -d`, and stop it when done.
- Apply the legacy migrations to it. Write the connection string into `legacy/.env.local` inside this worktree; commands containing `DATABASE_URL=` are blocked by the guard, but a file is fine. Then run `pnpm --dir legacy db:migrate`.
- Seed realistic data. Use legacy's `pnpm --dir legacy test:seed <email>` (settled wagers and a group) for two or three users, plus a handful of hand-written inserts for edge cases:
  - a user with no name;
  - a comment with quotes, an emoji and a newline;
  - a wager on a totals market (line 8.5);
  - a void settlement;
  - a reset at delta 0;
  - a group with a link invite and a revoked invite;
  - buddy messages and notes.
- Run export, transform, import into a **fresh local D1** (`pnpm db:migrate:local` on clean state, then `wrangler d1 execute DB --local --env preview --file migration-out/import.sql`), then reconcile against local. It must print `RECONCILE OK` and the ledger invariants must pass.
- Prove the import's trigger handling: after the import, `SELECT count(*) FROM credit_entries WHERE kind = 'grant'` equals the number of migrated users, and creating a brand-new user afterwards still gets exactly one grant (the trigger is back).
- Add `pnpm migrate:export`, `pnpm migrate:transform` and `pnpm migrate:reconcile` scripts, and a short `scripts/migrate/README.md` with the exact commands for the production cutover (spec §7). Note there that `export-neon.ts` against production is run by Oscar or the coordinator, never by a builder.
