## Decisions already made (don't revisit)

- Drizzle sqlite dialect (`drizzle-orm/sqlite-core`, driver `drizzle-orm/d1`). `drizzle.config.ts` at the root: `dialect: "sqlite"`, `driver: "d1-http"` is NOT needed — only `generate` is used; output folder `drizzle/`. Generate with `pnpm drizzle-kit generate`. Apply locally with `pnpm wrangler d1 migrations apply DB --local --env preview`. Never `drizzle-kit push` or `migrate`.
- Type rules exactly as spec §3.6: uuid → `text`; timestamptz → `integer({ mode: "timestamp_ms" })`; jsonb → `text({ mode: "json" }).$type<...>()`; pg enums → `text({ enum: [...] })` **plus** a `check()` constraint; `wagers.price` → `price_hundredths integer` and `wagers.line` → `line_tenths integer`, each through a Drizzle `customType` that exposes a plain number (1.85 / 2.5) to code; `buddy_messages.fact_ids text[]` → `text({ mode: "json" }).$type<string[]>()`. `defaultRandom()` → `.$defaultFn(() => crypto.randomUUID())`; `defaultNow()` → `.$defaultFn(() => new Date())`.
- Keep every legacy table, column (renamed only where the type rule says), index, unique index and partial-index `WHERE` predicate. Index names stay the same.
- **Auth tables follow Better Auth's core schema** (tables `user`, `session`, `account`, `verification`, with Better Auth's column names), replacing legacy `users`, `sessions`, `accounts`, `verification_tokens`. Every legacy FK to `users.id` now points to `user.id`, with the same `onDelete` behaviour.
- Add a virtual generated column `games.status` = `json_extract(summary, '$.status')` and index it together with `scheduled_at`. Use the Drizzle `generatedAlwaysAs` API; if drizzle-kit can't express it, add it in a hand-written migration step (see below).
- **Starting-grant trigger** exactly as in spec §3.6, in a hand-written SQL migration after the generated one: create it with `pnpm drizzle-kit generate --custom --name starting_grant_trigger` and paste the trigger SQL. Use reason text `"starting grant"` unless `legacy/src/data/credits.ts` or `legacy/src/lib/auth.ts` uses a different reason string for the grant — then use theirs and say so in the log.
- Database access: `src/lib/server/db/client.ts` gets the binding with `import { env } from "cloudflare:workers"` (adapter-cloudflare 8 passes no `platform`; T00 confirmed `cloudflare:workers` works on the preview). Keep legacy's exported names: `isDatabaseConfigured()` (true when the `DB` binding exists), `getDatabase()`, `DatabaseConfigurationError`, `checkDatabaseConnection()` (port: tables from the schema, and pending migrations computed against the `d1_migrations` table and the bundled list of files in `drizzle/`). Drop `withDatabaseTransaction` and `setDatabaseForTests`; add `runBatch(statements)` that wraps `db.batch(...)`.
- Relative imports inside `src/lib/server/**` (same rule as T01).

## Pieces

1. `src/lib/server/db/schema.ts`: full schema per the rules above.
2. `drizzle.config.ts`, generated migration `drizzle/0000_*.sql`, custom migration for the trigger (and the generated column if needed). `wrangler.jsonc` already has `migrations_dir: "drizzle"`; keep drizzle-kit's `meta/` folder.
3. `src/lib/server/db/client.ts` as above.
4. `src/lib/server/db/seed.ts`: port of `legacy/src/db/seed.ts` (team seed, idempotent upserts).
5. `src/lib/server/data/sports-repository.ts`: port **all** exports of the legacy file. `persistSportsTeamData` becomes one `db.batch([...])` per team made only of upserts (`onConflictDoUpdate`) and inserts — no reads inside the batch. If the legacy transaction reads a value and then writes based on it, turn that into SQL in the statement (`excluded.*`, `CASE`, sub-select) and explain it in the log. `acquireRefreshLease`/`completeRefreshLease` keep their semantics using the partial unique index on `status = 'running'` (insert … on conflict do nothing, then check `meta.changes`) and the legacy stale-lease rule.
6. `src/lib/server/data/sports-data.ts`: port **only the read side**: `getTeamSchedule`, `getDashboardData`, `getGameDetail`, `getConfiguredTeams`, and the private helpers they use, with the fallback chain fresh → stale → demo, freshness derived from stored expiry, and the legacy runtime team seed. Remove `unstable_cache`, `after()` and `revalidateTag` (T03 adds KV read models). Where legacy triggers a refresh on a stale or cold read, leave a single call `scheduleRefresh(sport)` that is a documented no-op for now (T03 implements it). `MATCHDAY_DATA_MODE=demo` and a missing `DB` binding both serve the seed.
7. `package.json` scripts: `db:generate` (`drizzle-kit generate`), `db:migrate:local` (`wrangler d1 migrations apply DB --local --env preview`).
8. A temporary check route is NOT allowed. Prove things with `wrangler d1 execute DB --local --env preview --command "..."`.

## Acceptance (coordinator re-runs these; paste each command and its output in the log)

1. `pnpm check` prints `CHECK OK <sha>`.
2. `rm -rf .wrangler/state && pnpm db:migrate:local` applies every migration with no error.
3. `pnpm wrangler d1 execute DB --local --env preview --command "SELECT name, sql FROM sqlite_master WHERE type IN ('index','trigger') ORDER BY name"` lists each legacy index name (with its partial `WHERE` where legacy had one) and `user_starting_grant`.
4. Grant trigger: insert one `user` row, then `SELECT kind, amount FROM credit_entries WHERE user_id = '<id>'` returns exactly one `grant | 1000` row; a second manual `INSERT INTO credit_entries (..., kind) VALUES (..., 'grant')` for the same user fails on `credit_entries_user_grant_uidx`.
5. Return uniqueness: insert a wager and two `return` entries for it; the second fails on `credit_entries_wager_return_uidx`. Then `INSERT ... ON CONFLICT (wager_id) WHERE kind = 'return' DO NOTHING` succeeds with 0 changes.
6. Lease: two `INSERT`s of a `running` ingestion run with the same provider/operation/scope — the second is rejected by `ingestion_runs_active_lease_uidx`.
7. `pnpm wrangler d1 execute DB --local --env preview --command "PRAGMA foreign_key_list(wagers)"` shows `user_id → user(id)`.
