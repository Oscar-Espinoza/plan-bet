## Facts you need

- Some pieces may already exist, from T08a (`notifyGroupWagerPlaced` and a few group reads) and T08b (`listGroupsForUser`). **Extend those modules; don't duplicate them.**
- Legacy took `pg_advisory_xact_lock(5, group or token)` for creating or reusing a join link and for accepting. D1 has no locks, so turn each check into SQL predicates inside one `db.batch()`, using the same pattern as T08a's `placeWager`. Pre-reads only choose the error message.
  - **Accept:** `UPDATE group_invites SET status = 'accepted' WHERE token = ? AND status = 'pending' AND expires_at > ? [AND email matches when the invite has an email]`, then `INSERT INTO group_members … SELECT … WHERE EXISTS (the invite is now accepted by this request)`. Use `meta.changes` of the update to know whether this request claimed it. Expiry also updates `pending → expired` as legacy does.
  - **Revoke** keeps legacy's conditional `pending → revoked` update. Accept and revoke can never both succeed on one invite.
  - **Create or reuse a join link:** reuse the existing pending, unexpired link; otherwise insert one. Two concurrent requests must end with at most one pending link per group. Use a conditional insert, and if needed a partial unique index added in a **new migration** (`drizzle-kit generate`). Never edit migration 0000.
- `group_invites`, `group_members` and `groups` are **not** append-only (legacy updates invite status and the notify toggle). Wagers and the ledger are append-only, and this ticket never touches them except to read.
- Emails go through Resend over fetch in `waitUntil`, are skipped when `RESEND_API_KEY` is unset, and respect `notify_on_activity`. Never on the request's response path.
- Mutations: `isSameOrigin` → `requireAccount(event)` → `readJsonBody`, with the same envelopes and codes as legacy.
